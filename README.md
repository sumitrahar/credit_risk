# Credit Risk Portfolio Monitor

A credit-risk monitoring dashboard built from 5 synthetic bank tables (10,000 customers, 14,685 loan accounts), with two embedded AI features: **Ask the Portfolio**, a Gemini assistant that answers only from computed data, and **Anomaly Review**, a list of unusual accounts for an analyst to confirm or dismiss.

## Python version

Python 3.12 (built and tested on 3.12.13).

## Run it

```bash
pip install -r requirements.txt
```

```bash
python -m src.build
```

```bash
streamlit run app/app.py
```

The build takes about 2 minutes. Its outputs are also committed in `data/processed/`, `models/` and `docs/`, so the third command works on its own after the first. Run the tests with `pytest`, after the build.

## Setting the LLM API key

The assistant uses the Google Gemini API, and the free tier works. Create a key in [Google AI Studio](https://aistudio.google.com/apikey).

- **Locally:** copy `.env.example` to `.env` and set `GEMINI_API_KEY`. `.env` is ignored by git.
- **On Streamlit Community Cloud:** paste this into the app's Secrets settings:

  ```toml
  GEMINI_API_KEY = "your-key"
  ```

`GEMINI_MODEL` is optional and defaults to `gemini-3.1-flash-lite`, a stable model with a free tier. Free-tier models can be overloaded at busy times, so if a model returns a 503 or a rate limit, the app automatically tries `gemini-3.5-flash-lite`, `gemini-3.6-flash` and `gemini-3.8-flash`. If you turn on billing, set a spending limit, because the app is public.

**If no key is set,** the whole dashboard still works. Ask the Portfolio shows a notice and offers a **guided query**: dropdowns that run the same calculations with no LLM. The same guided query is the fallback if every model returns a rate limit (429) or another error, and if that happens part-way through a question, a code-written answer with the exact figures is shown.

## How Ask the Portfolio stays grounded

The LLM never calculates a number and never writes SQL.

1. **Route.** Gemini reads the question and must call one of three functions: `query_portfolio`, `get_account` or `decline`. It sees the catalogue of metric, dimension and value names, and no data rows.
2. **Compute.** `src/query_engine.py` validates the choice against that fixed catalogue and computes the result with pandas.
3. **Phrase.** Gemini sees only the result and writes 1-3 sentences.
4. **Check.** Every number in the sentence must appear in the result. If one does not, a code-written answer replaces it. The source line is always written by code, and the query is shown under each answer.

Questions the catalogue cannot answer are declined: loss given default, forecasts, "why" questions, and anything outside the portfolio.

`python -m tests.live_assistant_eval` tests this against the real API with a key: 31 answerable questions compared with direct calculations, and 17 unanswerable questions that must be declined. Normal `pytest` runs use a fake LLM and never call the API.

**What is sent to Google:** the question text, the catalogue, and the computed result (aggregates, or one account's score, band, drivers and flags). Customer IDs and raw tables are never sent. The free tier may use content to improve Google's products, which is acceptable for synthetic data only. Production would need a paid or enterprise tier.

## Join logic

The analysis dataset has exactly one row per loan account. A test confirms it stays at 14,685 rows, and the build stops if a key is duplicated or orphaned.

| Table | Rows | Joined to | On | How |
|---|---|---|---|---|
| `customers` | 1 per customer | `loan_accounts` | `customer_id` | One customer to many loans. Left join from loans, so no account is lost. |
| `repayment_history` | 12 per account | `loan_accounts` | `account_id` | Aggregated to one row per account first. |
| `bureau_credit` | 0-9 per customer | `loan_accounts` | `customer_id`, limited by date | Aggregated per account. Only lines opened by origination + 12 months count, and lines closed or written off after that date are treated as still Active. These are the model's features. |
| `bureau_credit` | 0-9 per customer | `customers` | `customer_id` | A second, current view for anomaly detection and monitoring. Never a model input. |
| `collections_events` | 0-3 per account | `loan_accounts` | `account_id` | Aggregated per account and left-joined. Display only: never a model input. |

## Portfolio insights

<!-- INSIGHTS:START -->
1. **Mortgages are the concentration risk.** Mortgages are 9.8% of accounts but 52.3% of originated exposure and 65.0% of defaulted dollars. Their 24.7% default rate is the highest of any product (others: 13.9% to 16.2%) even though they are secured, and 240-month mortgages reach 29.2%. *So what:* Review mortgages first and tighten long-term underwriting. Collateral values are needed from the bank, because the actual loss cannot be sized without them.
2. **Income and employment together separate risk.** Default falls from 32.4% under $40k to 9.5% at $100k+. Unemployed borrowers are 4.9% of accounts but 10.6% of defaults. Unemployed mortgages default at 54.3% (70 accounts, $15.6M). Contract borrowers run 35.1% under $40k but 12.8% at $60-80k. *So what:* Apply a hard policy rule to mortgages for unemployed applicants, and assess contract workers by income rather than treating them as one group.
3. **Pricing does not reflect income risk.** The average interest rate is 11.8% to 12.0% in every income band, while default rate runs from 9.5% to 32.4%. Within personal loans, rate and income are uncorrelated (r = -0.02). *So what:* The strongest risk driver in the portfolio is not priced in, so low-income borrowers are under-charged for their risk. A risk-based pricing review is worth testing.
4. **Delinquency alerts miss nearly half of defaults, and collections are not targeted.** 46.7% of defaulters never missed a payment in 12 months. Only 38.0% of defaulted accounts had any collections action, while 3,380 non-defaulted accounts did. Recoveries equal 0.99% of defaulted loan amounts. *So what:* Prioritise collections by model score rather than by missed payments alone, and audit the collections data first: 44.9% of events are dated before the loan began.
5. **Region is not a useful lever; age is, with a caveat.** Regions span only 15.0% to 16.9% (channel 15.4%-16.9%, purpose 14.9%-16.9%, sector 15.0%-17.0%). Age falls from 22.2% at 21-25 to 10.6% at 56+, and the gradient holds within every product. *So what:* Drop region-based risk strategy. Age predicts default but raises fair-lending concerns, so it needs compliance review before any use in decisions.
<!-- INSIGHTS:END -->

## Model results

Validated with 5-fold cross-validation grouped by customer, because customers hold several loans and one default predicts another. Scores in the dashboard are out-of-fold, so no account is scored by a model that saw its own customer. The out-of-time test trains on 2018-2021 and tests on 2023, excluding customers seen in training.

## Key assumptions

- The data is a snapshot at 2025-12-31, because the latest bureau line opened on 2025-12-29.
- Default is observed after month 12, because the target has no date and many defaulters never missed a payment. That makes the model a month-12 behaviour score. Sensitivity for 3 and 6 months is above.
- Status, balance and days past due on Active bureau lines are as at last reporting, which has no date. This small look-ahead cannot be removed with the data provided.
- Latest balance is approximate, because balances fall by a fixed 60% of each payment.
- Gender, marital status, region and age are left out of the model pending compliance review.

## Known limitations

- Analyst decisions are stored in SQLite on the app's own disk. Free hosting can reset that on a restart or redeploy, so the app offers a CSV export. Production would use a shared database.
- Streamlit Community Cloud puts an app to sleep after 12 hours without traffic. Anyone viewing it can wake it with one click.
- Gemini's free tier has rate limits and can be overloaded. The app tries other models first, then falls back to the guided query.
